# 状态管理

> 没有 Pinia,也暂时不需要。状态按「最小可见范围」放置,层级从小到大逐级升级,禁止跳级。

---

## 状态层级(从小到大)

| 层级 | 手段 | 现有例子 |
|------|------|----------|
| 组件内部 | 局部 `ref` / `computed` | `SearchInput.vue` 的 `inputRef` |
| 父子之间 | props 下行 + emit 上行 | `ResultsPanel` → `ToolSection` → `ToolTile` |
| 功能模块内多组件 | composable 内部状态,经返回值分发 | `useClipboardPage` 的列表/选中/过滤 |
| 跨组件共享 | 模块级 `ref` + 无参 composable | `useToolView`(工具页态)、`useKeymap`(快捷键表) |
| 全局 store | Pinia | 尚未引入;确有多模块复杂共享再讨论 |

数据流向纪律:父传子用 props,子通知父用 emit,不直接改父级状态;层级很深才考虑 provide/inject(当前无使用)。

---

## 状态归属要写清楚

同类状态分属不同 owner 时,归属与交接规则必须写在字段文档注释里。基准示例是「两份搜索词」:

- `homeQuery`(`useLauncher`):主页全局搜索词
- `toolQuery`(`useToolView`):工具页内过滤词

两者的交接在注释中逐条写明:打开 view 型工具时主页词是否带入、退出是否写回、何时清空(见 `useLauncher.ts` 与 `useToolView.ts` 开头的注释)。新增状态时同样要求:**读注释就能回答「谁改它、何时复位」**。

---

## 保留现场原则

启动器「收起」只是隐藏窗口,**不是**组件卸载,状态默认保留:搜索词、所在页面、滚动位置、选中项在下次唤起时原样恢复(`useLauncher.ts`、`useClipboardPage.ts` 的注释均有声明)。

- 复位是显式动作,只发生在明确定义的时机:查询变化时选中归零(`useResults` 的 `watch(query, () => reset())`)、列表整表重置时滚动回顶(`refreshTick` 计数器)
- 新增页面状态时先决定:窗口隐藏→唤起要不要保留?保留是默认,复位要有理由并写注释

---

## 与后端状态同步

后端(SQLite)是事实源,前端列表是它的**本地镜像**,同步遵循三条通道(实现见 `useClipboardPage.ts`):

1. **事件推送**:后端落库后 emit 预览载荷,前端按 id 合并(已存在则上浮)
2. **自发变更本地镜像**:自己触发、后端抑制回推的变更(粘贴刷新 `lastUsedAt`),前端同步模拟(`mirrorTouch`),保持首条比对一致
3. **唤起校验**:窗口再次唤起时拉首屏只比对首条 id,对得上不重置(保滚动/选中),对不上说明隐藏期间漏了事件,整表重拉

衍生约定:凡是「前端模拟后端行为」的代码,注释必须说明模拟的是后端哪个动作、为何不能等回推。

---

## 派生状态单一来源

同一份数据的多种形态用 `computed` 从单一定义派生,不各自维护。基准示例:`useResults` 的分区定义一次性「盖章」全局下标,`sections`(模板渲染)与 `rows`(键盘导航)都从它派生,顺序与下标结构上不可能错位。模板里需要的展示形态(键帽标签、空态文案)同样用 computed 派生,不存第二份。

---

## 引入 Pinia 的门槛

出现以下情况前不引入:≥3 个功能模块要共享同一份可变状态、需要 devtools 时间旅行调试、或模块级 ref 的测试隔离成为实际痛点。引入时先在任务 PRD 里说明动机。
